# 系统升级设计文档

**基本信息**  
- 原系统类型：待办事项清单（单用户单机版）  
- 技术栈：SpringBoot + MySQL + Thymeleaf + JPA  

---

## 一、需求分析：原来哪里不好用

之前的待办事项系统是单页面应用，所有数据存在同一张 `todo_item` 表里，存在以下问题：

1. **无用户体系**：任何人打开页面就能看到全部数据、随意增删改，没有登录机制和数据归属概念
2. **误删不可恢复**：删除操作直接执行物理 DELETE，数据从数据库永久移除，用户手滑误删后无法找回
3. **操作效率低**：只有逐条操作按钮，面对多条待办时只能一条条点击，缺乏批量处理能力

**升级目标**：将单用户单机版升级为支持多用户登录注册、数据隔离、软删除可恢复、批量操作的管理系统。

---

## 二、架构调整：改了哪些地方

### 2.1 整体架构
保持原技术栈不变（SpringBoot + MySQL + Thymeleaf），在原有三层架构（Entity → Repository → Service → Controller）基础上新增：
- **权限管理**：Session 拦截器 + 角色区分
- **批量操作**：批量删除、批量标记完成
- **回收站**：软删除标记 + 回收站独立页面

### 2.2 数据库 Schema 变更

**新建 `user` 表**：
```sql
CREATE TABLE user (
    id       BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50)  NOT NULL UNIQUE,
    password VARCHAR(100) NOT NULL,   -- BCrypt 加密
    role     VARCHAR(20)  NOT NULL DEFAULT 'USER'  -- ADMIN / USER
);
```

**`todo_item` 表新增字段**：
- 新增 `user_id`（BIGINT）：数据归属，外键关联 user 表
- 新增 `deleted`（BOOLEAN，默认 FALSE）：软删除标记
- 新增 `deleted_time`（DATETIME）：删除时间戳

## 三、功能模块详细设计

### 3.1 权限管理模块

**权限模型**：基于角色的访问控制（RBAC），区分 ADMIN（管理员）和 USER（普通用户）两种角色。

**认证方式**：采用 Session + 自定义拦截器，不引入 Spring Security 框架，仅使用 `spring-security-crypto` 做 BCrypt 密码加密。

**控制层级**：
- **路由层**：`LoginInterceptor` 拦截 `/**` 所有路径（排除 `/login`、`/logout`、`/register`），检查 session 中是否有 user 对象，未登录跳转登录页
- **业务层**：所有数据操作校验归属权——普通用户只能操作 `user_id == 自己` 的数据，管理员不受此限制
- **界面层**：导航栏根据 `session.user.role` 控制"用户管理"入口的可见性；回收站中管理员额外显示"创建者"列

**关键逻辑示例**：
```java
// 普通用户只看自己的未删除数据
List<TodoItem> findByUserIdAndDeletedFalseOrderByCreateTimeDesc(Long userId);

// 管理员看全部未删除数据
List<TodoItem> findByDeletedFalseOrderByCreateTimeDesc();
```

**预置账号**：应用启动时若 user 表为空，自动插入 admin/admin123（管理员）和 user/user123（普通用户）。

### 3.2 批量操作模块

**功能范围**：批量删除（软删除）、批量标记完成/撤销、批量恢复、批量彻底删除。

**交互设计**：
1. 列表每行前增加 checkbox，顶部有全选 checkbox
2. 顶部显示「批量标记」和「批量删除」按钮
3. 点击后弹出确认对话框，显示选中条数
4. 确认后动态构造 POST 表单，将 ID 数组提交到后端

**后端处理**：
- 接收 `List<Long> ids`，开启 `@Transactional` 事务
- 逐条校验数据归属（普通用户跳过不属于自己的数据）
- 统一调用 `saveAll()` 批量更新

### 3.3 软删除与回收站模块

**软删除机制**：
```java
// 不再执行 repository.deleteById(id)
item.setDeleted(true);
item.setDeletedTime(LocalDateTime.now());
todoRepository.save(item);
```

**查询过滤**：Service 层手动调用 `findByDeletedFalse...` 方法，而非 JPA `@Where` 注解（回收站查询时需要查已删除数据）。

**回收站数据隔离**：
| 角色 | 回收站显示 | 操作权限 |
|------|-----------|----------|
| ADMIN | 所有人的已删除记录 | 可恢复/彻底删除任意记录 |
| USER | 仅自己的已删除记录 | 可恢复/彻底删除自己的记录 |

**回收站操作**：
- **恢复**：`deleted = false, deletedTime = null`
- **彻底删除**：物理 DELETE，不可恢复
- **自动清理**：`@Scheduled(cron = "0 0 3 * * *")` 每天凌晨 3 点清理 `deletedTime` 超过 30 天的数据

## 四、功能联动设计（重点）

**典型场景 1**：普通用户在主列表勾选 3 条自己的待办 → 点击「批量删除」 → 确认弹窗 → 后端接收 ID 数组，`@Transactional` 事务内逐条设置 `deleted=true, deletedTime=now`，提交后页面刷新，3 条记录从主列表消失 → 用户点击「回收站」→ 看到刚才删除的 3 条记录 → 勾选后点击「批量恢复」→ 数据 `deleted` 改回 `false`，重新出现在主列表。

**典型场景 2**：管理员在回收站中看到不同用户删除的记录 → 可勾选多条跨用户数据 → 批量恢复或批量彻底删除 → 管理员不受 `user_id` 限制，事务统一处理。

**数据流向**：主列表（`deleted=false`）→ 软删除 → 回收站（`deleted=true`）→ 恢复 → 主列表。全程受权限控制，查询和操作链路一致。

## 五、技术难点与解决方案

**难点 1**：原有删除逻辑散落在 Controller 中，改为软删除需要全局替换
**解决**：统一收敛到 `TodoService.deleteById()` 中，Controller 只调用 Service，不直接操作 Repository。后续新增批量删除、回收站操作也全部走 Service 层。

**难点 2**：批量操作中部分数据不属于当前用户
**解决**：普通用户的批量操作在循环中跳过无权限的条目（`continue`），而非直接抛异常。这样既能保护数据安全，又不会因一条无权限导致整个批量操作失败。

**难点 3**：回收站页面需要同时展示数据内容、创建者、删除时间，且管理员和普通用户看到的列不同
**解决**：用 Thymeleaf 的 `th:if="${session.user.role == 'ADMIN'}"` 条件渲染"创建者"列，数据过滤在 Controller 层分叉处理。

**难点 4**：SQL 建表脚本与 JPA 实体定义不一致，新环境部署可能缺字段
**解决**：更新 `database/todo.sql` 使建表语句直接包含全部字段，同时保留 `ALTER TABLE ADD COLUMN IF NOT EXISTS` 兼容语句。日常开发依赖 JPA `ddl-auto=update` 自动同步。
